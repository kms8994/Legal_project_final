# 문서 세트 자체 피드백

## 1. 잘 반영된 부분

- 기존 문서의 MVP 방향을 더 명확히 고정했다.
- RAG 로직을 검색용, 비교용, 생성용으로 분리했다.
- 비교 후보 추천에서 사실관계와 material facts 유사도를 최우선으로 두었다.
- outcome difference는 낮은 가중치와 표시 조건으로 조정했다.
- 데이터 파이프라인을 대량 적재와 재처리 중심으로 설계했다.
- 백엔드, 프론트엔드, DB, UI/UX, 평가, 운영 문서를 분리했다.
- 각 문서에 완료 체크리스트를 넣어 구현 중 참조하기 쉽게 했다.

## 2. 아직 부족한 부분

### 실제 조문 목록은 초안 단계임

`StatuteScope.md`에 초기 후보를 정리했지만, 실제 API 수집 결과를 보고 최종 15~30개 목록을 확정해야 한다.

보완:

- 손해배상 도메인 핵심 조문 목록 문서를 별도로 만든다.
- 각 조문별 수집 예상 판례 수를 확인한다.

### 실제 데이터 소스 검증이 아직 없음

법령정보센터 API에서 원하는 법령, 조문, 판례가 어느 정도 수집되는지 확인해야 한다. 이 API는 런타임 백엔드가 아니라 로컬/배치 파이프라인에서만 사용한다.

보완:

- 5개 조문으로 수집 테스트를 진행한다.
- 목록 API와 상세 API 응답 형태를 확인한다.
- 중복률과 누락 가능성을 기록한다.

### material facts 스키마는 계속 보강 필요함

`MaterialFactsTemplates.md`에 세부 유형별 템플릿을 추가했지만, 실제 판례 구조를 보면서 필드를 조정해야 한다.

보완:

- 교통사고
- 사용자책임
- 공동불법행위
- 위자료
- 과실상계

각 유형별 material facts 템플릿을 만든다.

### 평가 데이터셋은 초안 단계임

`EvaluationSet.md`에 초안을 만들었지만, 실제 수집 판례 ID와 정답 라벨은 아직 없다.

보완:

- 조문 검색 10개
- 자연어 질문 20개
- 비교 기준 판례 10개

를 먼저 수작업으로 만든다.

### UI 와이어프레임이 없음

UI/UX 명세는 있지만 실제 화면 배치 그림은 없다.

보완:

- 검색 화면
- 결과 카드
- 비교 후보 카드
- 비교 분석 매트릭스

4개 화면의 간단한 와이어프레임을 추가한다.

### 인증/사용자 범위가 최소 정책 수준임

MVP에서는 결제를 제외했지만, 익명 사용자만 둘지 간단한 로그인까지 둘지 아직 명확하지 않다.

보완:

- 학기 프로젝트 MVP는 익명 사용자 + 로컬 user_id 또는 세션 ID로 시작한다.
- 로그인은 피드백 품질 관리나 사용량 제한이 필요해질 때 추가한다.

### BFF와 FastAPI 책임 경계가 구현 단계에서 흔들릴 수 있음

문서상으로는 BFF가 rate limit과 프록시를 담당하고 FastAPI가 검색/RAG를 담당하지만, 실제 구현 중 API shape 조정 책임이 중복될 수 있다.

보완:

- BFF는 인증, rate limit, 프록시, 프론트 응답 정리만 담당한다.
- 검색 점수, RAG, 비교 로직은 FastAPI에서만 담당한다.

### 화면 와이어프레임과 디자인 토큰이 없음

UI/UX 원칙은 있지만 색상, 간격, 카드 구조, 모바일 비교 레이아웃 기준이 아직 없다.

보완:

- `Wireframes.md` 작성
- 검색 결과 카드와 비교 후보 카드의 필드 순서 고정
- 모바일 비교 화면을 탭 또는 세로 스택 중 하나로 확정

### API 계약 테스트 기준이 아직 부족함

API 명세는 있지만 프론트와 백엔드가 같은 schema를 공유하는 방법이 아직 없다.

보완:

- FastAPI OpenAPI schema를 생성한다.
- 프론트 타입은 OpenAPI에서 생성하거나 shared-types에 수동 고정한다.
- API 응답 fixture를 만들어 프론트 개발에 사용한다.

### RAG/임베딩 검증은 구현 이후 과제로 남겨둠

임베딩 모델과 chunk 전략은 지금 문서에서 최종 확정하지 않는다. 실제 DB와 검색 API 구현 후 평가 세트로 검증한다.

보완:

- `DevelopmentPlan.md` Phase 7에 검증 작업을 추가했다.
- `EvaluationAndQA.md`에 임베딩 모델, chunk 전략, 가중치 실험 기준을 추가했다.

### 법률/저작권 검토가 문서 수준에 머무름

원문 표시 범위와 AI 요약의 2차 저작물 이슈는 실제 검토가 필요하다.

보완:

- MVP에서는 공식 링크 우선 정책을 유지한다.
- 원문 전체 노출은 하지 않는다.
- 근거 문단 일부 표시 범위를 제한한다.

### LLM provider와 임베딩 모델은 최종 확정 필요

문서에서는 provider adapter 구조와 768차원 단일 모델을 전제로 했지만, 실제 모델 선택은 남아 있다.

보완:

- 로컬 실행 가능 모델과 API 모델을 비교한다.
- 임베딩 품질을 평가 세트로 비교한다.

## 5. 현재 문서 기준 구현 리스크

- 데이터 수집량이 부족하면 비교 후보 품질이 낮아질 수 있다.
- material facts 추출 품질이 낮으면 사실관계 유사도 계산이 흔들린다.
- LLM 요약이 evidence를 제대로 따르지 않으면 신뢰 문제가 생긴다.
- UI에서 결과 차이를 너무 강조하면 사실관계 유사 비교라는 핵심이 흐려질 수 있다.
- 평가 세트를 늦게 만들면 품질 개선 방향을 알기 어렵다.

## 6. 결론

현재 문서 세트는 MVP 구현을 시작하기에 충분한 기준을 제공한다. 다만 실제 코딩 전에는 law.go.kr 수집 테스트, 화면 와이어프레임, 관리자 검수 정책을 추가하면 구현 중 판단 비용이 더 줄어든다.
